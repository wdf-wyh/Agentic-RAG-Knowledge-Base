# Demo Assets Checklist

如果你的目标是把这个项目往更高传播性、更容易获得 star 的方向推进，这份清单可以直接拿来执行。

## 目标

让第一次看到仓库的人，在 15 到 30 秒内完成三件事：

1. 知道项目解决什么问题
2. 看到它已经能用，而不是停留在概念
3. 明白为什么这个项目和其他 RAG demo 不一样

## README 首屏建议

建议在 `README.md` 顶部补这些素材：

- 一张首页主界面截图
- 一段 15 到 30 秒的 GIF
- 一句明确定位的话
- 一组直达链接：
  - `Quickstart`
  - `Docker Compose`
  - `Architecture`
  - `Roadmap`

## 最值得录的 3 段 GIF

### 1. 30 秒首次体验

流程：

1. 打开首页
2. 进入设置
3. 选择模型
4. 上传文档
5. 点击构建
6. 提一个问题
7. 展开来源

目标：放在 README 顶部，让用户一眼看懂完整链路。

### 2. 智能模式演示

流程：

1. 切到智能模式
2. 提复杂问题
3. 展开推理过程
4. 展示工具与结果

目标：突出你和普通文档 QA 项目的区别。

### 3. 本地优先部署演示

流程：

1. 展示 `.env`
2. 启动 `start.ps1` 或 `docker compose up`
3. 打开页面
4. 进行一轮问答

目标：降低“这个项目很难跑”的心理门槛。

## 推荐示例问题

录屏和截图尽量使用稳定、可复现的问题，不要用随机性太强的开放问题。

推荐：

- `请总结这批文档的核心主题，并给出 3 个结论。`
- `根据知识库内容，帮我写一份给新同事的入门说明。`
- `如果我要把这个系统部署到团队内部，最小可行方案是什么？`
- `这个项目支持哪些模型提供者？各自适合什么场景？`

## README 排版顺序建议

推荐顺序：

1. 标题
2. 一句话定位
3. 主界面 GIF
4. 核心卖点
5. 截图分区
6. Quickstart
7. Docker Compose
8. 架构说明
9. 路线图

## 发布前自检

- 截图里不要出现无效占位文案
- 截图里尽量使用真实知识库数据
- GIF 时长控制在 15 到 30 秒
- 首页截图要干净，不要打开开发者工具
- 回答内容尽量有来源、有结构、可复现
- README 顶部 1 屏内就能看到运行方式和主视觉
